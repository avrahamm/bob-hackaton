## 4. RPG/IBM i gotchas for a developer new to the platform

These will trip you up. Read them once before you write a line.

**Indicators (`*IN01`–`*IN99`, `*INLR`)**
- They are global. An indicator set in one procedure contaminates another unless you reset it. In free-format procedures, prefer explicit boolean variables over indicators wherever possible.
- `*INLR = *ON` is not optional — it must be set before your main program returns, or the activation group stays open and your file is locked on the next call.

**Subfile paging (`SFLPAG`, `SFLSIZ`, `SFLRCDNBR`)**
- You're not building new subfile UI, but you need to *understand* it to document the legacy screen. Key: `SFLPAG` ≤ `SFLSIZ`, and `SFLSIZ = SFLPAG` means no paging (one page only). The `SFLRCDNBR` keyword drives cursor positioning — it's why the search-and-position logic exists.
- `SFLDSP` and `SFLDSPCTL` are controlled by indicators and must both be on before you can display the subfile. Forgetting one produces a blank screen with no error.

**Date fields (`L` type / date data type)**
- `L` format is IBM i date. In RPG, date literals look like `D'2024-01-15'` (ISO by default). Conversion to/from character for SQL or JSON requires `%CHAR(date:*ISO)` and `%DATE(string:*ISO)`. Packed fields used as dates (legacy `6S0` YYMMDD) are different — your DDS uses `L` throughout, which is correct.
- JDBC maps `DATE` columns directly to `java.sql.Date`; Python `ibm_db` gives you `datetime.date`. JSON serialize as `YYYY-MM-DD` strings.

**Packed decimal (`P` type) and ODBC/JDBC**
- `PREMIUM(9P2)` is 9 digits, 2 decimal places. JDBC gives you `BigDecimal`; Python `ibm_db` gives you `Decimal` from the `decimal` module. In JSON, serialize as a number (not string) — `"premium": 1234.56`, never `"premium": "1234.56"`.
- Watch for implicit truncation: `(9P2)` max is 9999999.99. If test data exceeds this you get a data-mapping error, not a clean exception.

**`CHAIN`, `READ`, `READE` vs SQL**
- `CHAIN` is a keyed random read (like a primary-key lookup). `READE` reads next record with the same key — the foundation of your `getClaims` loop over `CLAIML1`. If you switch to embedded SQL (`EXEC SQL SELECT ...`) you can eliminate the logical file entirely, but you lose the "RPG native I/O" story. Both work; pick one and be consistent.
- `%EOF` after a `CHAIN` that finds nothing sets `%EOF = *OFF` but sets `%FOUND = *OFF`. Do not test `%EOF` for "record not found after CHAIN" — test `%FOUND` (or `*IN%XX` from the `CHAIN(E)` error indicator).

**Window keyword (`WINDOW`)**
- A display file with `WINDOW` requires a host record on a specific active display file to anchor to. This will not render in a batch program or called remotely. You will see `CPF5129` or a similar MCH escape message. Document it; don't try to call it from a service procedure.

**Activation groups**
- Service programs should use `ACTGRP(*CALLER)`. If you specify `ACTGRP(*NEW)`, resources (open files, static storage) are isolated per call, which is usually wrong for a called service program. `ACTGRP(*NEW)` on a service program called from a command entry will leave file locks when the caller ends without `*INLR`.

**`OPTION(*SRCSTMT *NODEBUGIO)` on CRTRPGMOD**
- Always compile with `DBGVIEW(*SOURCE)` during development so you can set breakpoints in STRDBG. Without it, debugging is line-number only — very painful.

**How JayDeBeApi returns result sets from `CALL`:**

This is a genuine subtlety. JayDeBeApi's behaviour depends on the stored procedure definition:

```python
cur = conn.cursor()
cur.execute("CALL ESH101.TEST_PROC2()")

# Case 1 — procedure uses OPEN cursor WITH RETURN TO CALLER
# JayDeBeApi advances to the result set automatically.
# You call fetchall() on the SAME cursor:
rows = cur.fetchall()   # ← works for WITH RETURN TO CALLER

# Case 2 — procedure uses WITH RETURN TO CLIENT (less common)
# You may need to call cur.nextset() first:
# cur.nextset()
# rows = cur.fetchall()
```

Your `TEST_PROC2` uses `WITH RETURN TO CALLER` (standard for most IBM i stored procs). The `test_jt400.py` script handles this correctly. **Watch for one gotcha:** if the procedure returns zero rows, `fetchall()` returns `[]` — not `None`. Check `len(rows)`, not `rows is None`.
